Context & Motivation

The Problem This Solves

Every late order starts a manual chase: check SAP stock, check purchase orders, check the logistics policy, decide whether to switch to air. It takes hours, and mistakes are expensive.

Before: Manual Workflow

  • Planner queries SAP for stock and open POs (15–30 min)
  • ATP calculation done manually in spreadsheet (error-prone)
  • Policy check requires consulting logistics manager (hours)
  • PO update submitted as change order in SAP (1–2 days)
  • No audit trail linking the decision to policy justification
  • Inconsistent decisions across planners and shifts

After: AI Agent Workflow

  • Single API call triggers the entire workflow (seconds)
  • Deterministic ATP logic mirrors SAP's calculation engine
  • Policy enforcement is automated and plant-specific
  • Minimum POs switched: cost impact kept to a minimum
  • Full trace of every agent decision and tool call returned
  • Consistent: temperature=0 keeps routing repeatable; the numbers never depend on the LLM

Domain: Available-to-Promise (ATP)

ATP is a core SAP supply chain function: "Can we promise this customer their X units by date Y?" The answer depends on current unrestricted stock, minus committed open sales orders, plus expected incoming purchase orders, walked in date order until coverage is reached. This system replicates that logic in Python, then adds AI reasoning on top for escalation decisions.

Core AI Logic

Where the Intelligence Lives

Three layers of intelligence work together: deterministic supply chain math, policy reasoning by language model, and a cost-aware PO selection algorithm.

ATP Algorithm

Mirrors SAP's native ATP calculation. Deterministic: no LLM in the math.

available_now = stock − Σ(open SOs)
IF available_now ≥ qty → fulfill today
ELSE walk POs by delivery date:
  cumulative += PO.qty
  IF cumulative ≥ qty → earliest_date = PO.eindt
  on_time = (earliest_date ≤ requested_date)

Break-Even PO Selection

When switching to AIR, only the minimum necessary POs are updated. POs fully absorbed by committed sales orders are never touched.

// Phase 1: skip SO-absorbed POs
WHILE running < 0: absorb POs, skip

// Phase 2: switch break-even → decisive
FOR remaining POs:
  SWITCH to AIR
  IF coverage ≥ qty → STOP

Policy-as-a-Document

Air freight authorization rules live in a Markdown file, not in code. The Policy Agent reads it at runtime and reasons about the specific plant. This means rules can be updated by a logistics manager without a code deploy.

TW01 — Always permitted JP01 — Permitted ≤14 days late SG01 — Permitted if qty > 500 TW02 — Blocked (cost ceiling) MY01 — Blocked (cost reduction active)

Full Auditability: Every Decision is Traceable

The API response includes both an answer (plain-English summary) and a trace (full message log of every agent action, tool call, and reasoning step). This is critical for enterprise supply chain: compliance teams can reconstruct exactly why a PO was switched, which policy clause authorized it, and what the stock position was at decision time.

The Full Planner Workflow

feasible fallback block / escalate early exit planner step

Waterfall: cheapest fix first

  • Credit hold is checked before anything else.
  • Stock already at the destination: answer right away.
  • Air only upgrades an existing sea order. It is not a source of stock.
  • Other plants: duty-paid (完稅廠) plants first, then lowest freight.
  • Production, rework and shortage are escalation steps, each with a named owner.
  • A planner approves every action.

Parallel: check everything, then rank

  • Destination stock is still checked first.
  • All other sources are queried at the same time.
  • Options are ranked by cost, then confidence, then arrival date.
  • The planner picks one option or a combination.

Design only. The prototype runs one step at a time.

Waterfall or parallel? The design keeps both.

Waterfall

Steps run one at a time in a fixed order and stop at the first option that meets the date. Predictable, deterministic and easy to audit.

Parallel

All sources are checked at once and the options are ranked for the planner. Often closer to how planners gather information in practice, though not always necessary.

Open question: when each mode should be used in real operations is not decided yet. That call needs input from senior planners, so both modes stay in the design until it is validated.

Scope & Boundaries

Assumptions & Known Constraints

This is a working prototype with deliberate scope boundaries. Each assumption below represents a known gap with a clear production path.

🗄️

Mock Database (SQLite)

SAP data is simulated with seed records. No live SAP RFC/BAPI connector. Production requires SAP integration via PYCO or OpenAPI wrapper.

🏭

Single-Plant Scope

ATP logic handles one plant (werks) per request. Multi-plant allocation and network-level fulfillment are out of scope.

📦

Unrestricted Stock Only

Uses SAP's labst (unrestricted) field. Quality inspection, blocked, and in-transit stock are excluded — matching standard ATP convention.

💱

No Freight Cost Comparison

Switching to AIR is authorized by policy, not by computed ROI. A production build should integrate freight rate APIs for cost-benefit gating.

↩️

No Rollback / Change Approval

PO method changes write directly to DB. Production requires SAP change order workflow with approval steps and rollback capability.

⚡

Synchronous / Single-Threaded

LLM calls are blocking. SQLite doesn't support concurrent writes. Suitable for demo load only — not high-volume production.

🔐

No Authentication

The /atp-check endpoint has no API key, rate limiting, or role-based access. Any caller can trigger PO changes in the current prototype.

🌊

SEA→AIR Escalation Only

The system escalates freight; it does not de-escalate. A PO switched to AIR cannot be reverted automatically — that requires a manual SAP change order per policy.

Why temperature=0?

Supply chain routing decisions should be reproducible. Temperature=0 minimizes randomness in the LLM's routing. It isn't a hard guarantee, so quantities, dates and PO selection are computed in Python and never depend on the LLM. This is a deliberate product decision, not a default.
